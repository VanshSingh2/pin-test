# YouTube→Shorts clip pipeline + Pexels b-roll route for Creative Director

This commit bolts a self-contained "paste a YouTube link, get vertical Shorts back" pipeline onto the existing Telegram Creative Director workflow, adds a `pexels` stock-footage option to the video visual-source routing, and hardens three switches with fallback outputs so unmatched routes stop dead-ending. The clip pipeline is a 14-node linear chain (download → transcribe → LLM moment-ranking → per-clip FFmpeg render → send) hung off a new `❓ Is YouTube Clip?` gate at the very front of the flow. The prompt edits (Director Brain, Master Brief) are copy/variety tweaks plus one contract-relevant change: `📋 Parse Director` can now emit `visual_source='pexels'`, which the `🔀 Visual Source` switch now has a branch for.

Watch for: (1) **confirmed** — any Telegram message whose text contains a YouTube URL is unconditionally diverted into the clip pipeline, bypassing the Director entirely, even mid-conversation or when the link is incidental. (2) **confirmed** — the Pexels scene branch has no empty-result guard and `neverError` is on, so a missing/invalid `PEXELS_API_KEY` or a query with no portrait clip silently produces blank solid-color scenes with no warning to the user. (3) **confirmed** — the clip pipeline runs outside the active-job-token in-flight guard the rest of the workflow uses, so clip renders neither dedupe nor interrupt concurrent jobs.

## High-level view

The entry rewiring is clean: `🧠 Intake` now feeds `❓ Is YouTube Clip?`, whose false branch goes to `❓ Has Reference Photo?` — exactly the node Intake used to feed in the parent. The entire downstream approval-gate and posting flow is untouched; the clip pipeline is a terminal side-branch that ends at `💬 Clip: Send` and never rejoins the main flow. The one behavioral catch is the gate condition itself: it fires on `ytUrl` being non-empty, and `ytUrl` is extracted by a regex that matches a YouTube URL *anywhere* in the message text, so incidental links hijack the Director.

Data passing through the clip chain is correct where it most easily breaks: `chatId` is threaded through `🧩 Clip: Prep` into every downstream node by explicit `$('🧩 Clip: Prep')` references, binary audio/video hand off on matching property names, and the fan-out at `📤 Clip: Explode` pairs to `💬 Clip: Send` via `$('📤 Clip: Explode').item` rather than relying on `$json` surviving `📂 Clip: Read MP4`.

The three switch edits are index-aligned with their connections. `🔀 Visual Source` gained a `pexels` rule at output 3 wired to `📷 Scene: Pexels Clip`, correctly pushing the pre-existing `extra` fallback down to output 4; `🔀 Content Type` and `🔀 API Route` gained `extra` fallbacks wired to their respective "unknown/not supported" replies. No off-by-one.

The `pexels` contract is consistent end to end: `📋 Parse Director`'s ROUTE_MAP maps `video_route='pexels'` to `visual_source='pexels'` + `render_engine='ffmpeg'`, and `📋 Scene: Pexels Ready` emits the same `{idx, narration, on_screen_text, image_url, clip_url}` shape the AI branch produces. The gap is failure handling, not wiring: unlike the Pinterest branch, Pexels has no scrape-OK gate, so empty results degrade silently.

### The clip gate fires on any embedded YouTube URL

`🧠 Intake` extracts `ytUrl` with a regex that scans the whole message text for a YouTube/`youtu.be` URL and returns the first match. `❓ Is YouTube Clip?` then routes to the clip pipeline whenever `ytUrl` is `notEmpty`. The consequence (confirmed) is that *any* message containing a YouTube link — "make me a video in the style of youtube.com/watch?v=…", "here's a reference: youtu.be/…", a link pasted mid-conversation — is diverted into the clip pipeline and never reaches the Director. The Director Brain prompt even acknowledges this blind spot ("you won't normally see bare links"), which suggests the hijack is known but not fully contained. Gating on the link being the sole/primary content of the message, or on an explicit "clip this" intent, would make the trigger predictable.

### Pexels branch degrades silently on empty results

The Pinterest scene branch routes through `❓ Scene Scrape OK?`, which diverts to `💬 Telegram: Scrape Failed (Scene)` when no clip URL is found. The new Pexels branch does not: `📋 Scene: Pexels Ready` wires straight into `🎞️ Video: Build FFmpeg`. When `📷 Scene: Pexels Clip` returns no portrait video — no results for the query, or a missing/invalid `PEXELS_API_KEY` — `clip_url` comes back empty. Because the request has `neverError: true`, the auth/no-result case throws nothing. `Build FFmpeg` then hits its `else` branch and substitutes a solid color background (`color=c=0x111418`), so the render succeeds and the user receives a finished video with blank scenes and no indication anything went wrong (confirmed by reading both nodes). The AI branch tolerates this because it always has a generated image; Pexels has no such guarantee. A guard mirroring the Pinterest path, or a notification when `clip_url` is empty, would surface the failure.

### Data flow through the clip chain

```
Intake ──► Is YouTube Clip? ──true──► Clip: Ack ──► Clip: Prep ──► Clip: Download (yt-dlp+ffmpeg)
                    │                                    │
                  false                          Read Audio ──► Transcribe (Whisper, binary "data"→"file")
                    ▼                                    │
            Has Reference Photo?              Rank Prompt ──► OpenRouter Clip Ranker ──► Parse Moments
            (unchanged main flow)                     │
                                          Build FFmpeg ──► Render ──► Explode ──(N items)──► Read MP4 ──► Send
```

`chatId` reaches every node via explicit `$('🧩 Clip: Prep').first().json.chatId` lookups rather than `$json` propagation, which is what keeps it intact across the HTTP and executeCommand hops that reshape the item. Binary handoffs line up: `📂 Clip: Read Audio` writes property `data`, `🎙️ Clip: Transcribe` reads `inputDataFieldName: data`; `📂 Clip: Read MP4` writes `data`, `💬 Clip: Send` sends `binaryPropertyName: data`. The fan-out is the part most likely to break: `📤 Clip: Explode` emits one item per clip, `📂 Clip: Read MP4` reads per-item via `$json.clipPath`, and `💬 Clip: Send` pulls `chatId` and `captionText` from `$('📤 Clip: Explode').item` — so even with Read MP4 sitting between them, the paired-item chain resolves each video to the right caption and chat instead of depending on `$json` surviving the read.

### Switch index alignment

`🔀 Visual Source` went from 3 rules + `extra` fallback (fallback at output 3 → `🎥 AIV: Scene Image`) to 4 rules + `extra` fallback. The new `pexels` rule takes output 3 → `📷 Scene: Pexels Clip`, and the fallback correctly moved to output 4, still → `🎥 AIV: Scene Image`. The connection array matches one-for-one, so adding the rule did not shift the fallback out from under its wire.

`🔀 Content Type` previously had no fallback (`fallbackOutput: none`), so an unrecognized `content_type` dead-ended with no output; it now uses `extra` with output 3 → `💬 Reply: Unknown Type`. `🔀 API Route` gained an `extra` fallback at output 3 → `💬 Reply: API Not Supported`. Note that the `buffer_fallback` rule in `🔀 API Route` (output 2) routing to `💬 Reply: API Not Supported` is unchanged from the parent and thus out of scope, though the name still implies it should fall back to Buffer posting rather than reject.

### Concurrency: clip pipeline skips the job-token guard

The main creation flow uses `💾 Set Active Job Token` / `❓ Job In Flight?` / `📥 Fresh Token Check` to dedupe and interrupt overlapping jobs. The clip pipeline (confirmed) contains none of these — it goes straight from the gate to download/render/send. A clip job can run for several minutes (download + Whisper + LLM + per-clip FFmpeg), and during that window a second pasted link, or a link pasted while a normal generation is mid-flight, will run concurrently with no dedup or interrupt. This is new behavior rather than a regression, but it's inconsistent with the concurrency model the rest of the workflow enforces.
